# About this fork

This is Molly's fork of [libsignal](https://github.com/signalapp/libsignal), Signal's cryptography and protocol API, maintained here for the client, server, and Android library targets.
It tracks upstream releases and diverges only where Molly requires it.

This file is the fork's handbook: the code conventions, the divergence catalog, and the procedures.

Each divergence is documented in this file, once, in the section where it belongs: why it exists, how it is kept across upstream merges, and which upstream changes it should anticipate.
A divergence is retained only as long as the underlying rationale remains valid.

## Code conventions

- New implementation is placed in fork files to minimize conflicts. Only the wiring is placed in upstream files.
- Upstream copyright headers are kept in upstream files.
- Fork files carry the `Copyright ... Molly Instant Messenger` line and the `SPDX-License-Identifier: AGPL-3.0-only` header.
- A `MOLLY:` prefixed comment explains divergences that are not evident at the site. Evident changes and procedure-covered divergences carry no comment.
- The authoritative inventory of divergences is the tree diff against the last merged upstream tag (`git diff vX.Y.Z HEAD`), and the catalog of reasons is this file. `git grep -n 'MOLLY:'` lists only the sites requiring a comment.

## Feature policy

Runtime behavior of the libraries for downstream users. Build defaults and artifact contents belong under Infrastructure.

### Proxy-only networking

`rust/net/src/connect_state.rs`: `infer_proxy_mode_for_config()` always returns `DirectOrProxyMode::ProxyOnly`.
Upstream falls back to a direct connection when a SOCKS proxy was configured at the system level or provided as an environment variable.
The Molly app allows configuring a SOCKS proxy at the app level and routes everything, DNS included, through it. A silent fallback to a direct connection would leak traffic outside the user's chosen proxy, so the fallback is removed.
Future upstream work on route selection (new proxy modes, new fallback conditions) might silently revert this policy.

## Infrastructure

Build configuration, CI, and distribution.
The codebase is shared between Signal and Molly, but each project operates its own infrastructure.

### Build

- Builds run in Docker and are reproducible: `Dockerfile.android`, driven by `Makefile` and `mk/android.mk`; `make help` lists the targets.
- JVM (client, server) and Android libraries are supported. Upstream also supports the iOS (`swift/`) and Node (`node/`) platforms; their sources remain, but nothing here builds them.
- Toolchain pins live in `Dockerfile.android`; `java/android`'s `compileSdk` and `ndkVersion` must stay in sync with them (noted in place).
- Upstream's Java builders (`java/Dockerfile`, `java/Makefile`, `java/docker/`) are deleted, replaced by this one.
- `java/gradle.properties` sets `crossCompileServer=true`: the server library is cross-compiled to x86_64 and aarch64 by default.
- Gradle dependency verification is strict. Upstream downgrades it to lenient by default in `java/gradle.properties`. This fork omits that, so the checksums in `java/gradle/verification-metadata.xml` always apply. When dependencies change, add the missing checksums from Gradle's own "Generated by Gradle" output.
- Android ABIs are `arm64-v8a`, `armeabi-v7a`, `x86_64`. Upstream's `x86` is dropped (`java/build_jni.sh`).
- `.dockerignore` excludes `.git` and build output directories.

### CI

- `build.yml`, `release.yml`, and `sync.yml` are fork-owned, as is `.github/actions/disk-cleanup/`.
- `build_and_test.yml` is upstream's workflow, cleaned to match the fork's supported targets and build.
- `lints.yml` is upstream's, lightly adapted.
- `build.yml` builds the Docker image and runs `assemble` inside it on push to `main`, exporting the Maven repository as a workflow artifact.

Upstream's other workflows are deleted, along with its workflow README, funding, actionlint config, and cargo-cache actions.

### Distribution

- Maven group `im.molly` (upstream: `org.signal`), publications named per artifact: `android`, `client`, `server` in `java/(android|client|server)/build.gradle`.
- Publishing goes to the staging repository, hosted on Cloudsmith (`https://maven.cloudsmith.io/mollyim/libsignal/`), authenticated with `CLOUDSMITH_USER` / `CLOUDSMITH_API_KEY`. Staged artifacts are not PGP-signed.
- The POMs point at `github.com/mollyim/libsignal` and an `organization` block with `https://molly.im`.

## Versioning

The repository's branches, tags, and the fork's version scheme.

### Branches and tags

- `main`: the fork mainline; upstream releases are merged into it directly.
- `upstream`: a mirror of upstream `main`, refreshed daily by `.github/workflows/sync.yml`.
- `vX.Y.Z` tags: upstream annotated release tags.
- `vX.Y.Z-N` tags: this fork's releases; `N` is the fork's release number for a given upstream version: `1` for the first release of a new upstream version, incremented for each further release of the same upstream version.

### Version scheme

The fork version is `<upstream version>-N`, hardcoded.
Upstream scripts (`bin/update_versions.py`, `bin/prepare_release.py`) are not used.
Keep the version identical in these places:

1. `Cargo.toml`: `[workspace.package] version`
2. `rust/core/src/version.rs`: `pub const VERSION`
3. `java/build.gradle`: `allprojects { version = ... }`
4. `Cargo.lock`: the fork-versioned crates (the workspace crates inheriting `[workspace.package] version`, found by `git grep -l '^version\.workspace = true' -- '**/Cargo.toml'`)

## Merging upstream

The routine work of this fork.

1. Merge the new `vX.Y.Z` tag into `main` and resolve the conflicts (classification table below).
2. Account for every divergence that existed before the merge. The full inventory is the diff against the last merged upstream tag.
3. Bump the version to `X.Y.Z-1` in the places listed under Version scheme, inside the merge commit.
4. Conclude with a merge commit titled `Merge upstream vX.Y.Z`, its message noting every resolution that took a judgment.
5. Verify the result (see Verification).
6. Release separately, by pushing the `vX.Y.Z-1` tag (see Releasing).

To resolve a conflict, classify both sides by the reasons documented in this file. The table below is a guide, not an exhaustive list:

| Upstream change                                                                                 | Resolution                                                                                                           |
|-------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------|
| Deleted upstream code, the policy holds                                                         | Keep it deleted                                                                                                      |
| Upstream's new code supersedes the policy (covers the need, converges on why the fork diverged) | The divergence vanishes: take upstream's, drop the fork's counterpart, and note it in the merge commit               |
| Upstream rewrote the area a fork change lives in                                                | Reapply the fork's change onto the new code, guided by the rationale in this file, keeping the site comment          |
| Upstream moves against a fork policy                                                            | Keep the fork's position, including removing the contradicting addition                                              |
| Upstream implements what the fork already implements, differently                               | Decide: convergence (take upstream's, note it in the merge commit) or divergence (keep the fork's, document it here) |
| Build-system fundamentals the build needs (new Gradle plugins, toolchain or layout changes)     | Port them into the fork's machinery, which drives upstream's build rather than replacing it                          |
| Upstream's own operations (CI, publishing, release scripting)                                   | Do not apply here; keep removed areas removed                                                                        |

Mechanical resolutions, no classification needed:

| Case                                                                          | Resolution                                                                                                        |
|-------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------|
| Identity strings (version, Maven group, POMs): everything under Distribution) | Keep the fork's                                                                                                   |
| `Cargo.lock`                                                                  | Take upstream lockfile, then re-stamp the fork-versioned crates                                                   |
| `java/gradle/verification-metadata.xml`                                       | Union-merges (`merge=union` in `.gitattributes`); afterward, verify that no needed checksum went missing          |
| Generated bridge files (`linguist-generated` in `.gitattributes`)             | Never hand-merged: regenerate (`just generate-jni` / `generate-ffi` / `generate-node`) or take one side wholesale |

Proven conflict-prone in past merges: `java/build.gradle`, `.github/workflows/build_and_test.yml`, `Cargo.lock`, `java/build_jni.sh`, `rust/net/src/connect_state.rs`, `justfile`, `java/(android|client|server)/build.gradle`, `java/gradle/verification-metadata.xml`, the generated bridges.

## Verification

- Run `make test` (`./java/gradlew -p java build`) to build and test the Java and Android libraries.
- Run `cargo build --workspace` and `cargo test --workspace --all-features` locally, with protoc on `PATH`.
- In CI, `build_and_test.yml` runs the above on push and PR, `lints.yml` runs the linters.

## Releasing

- Push a `vX.Y.Z-N` tag to trigger `.github/workflows/release.yml`: the Docker builder runs `stage` with the credentials from the repository secrets, publishing the artifacts to Cloudsmith.
- For a further release of the same upstream version, land the fixes on `main`, bump `N` in the places listed under Version scheme in a regular commit, and push the new tag.
- `make stage` is the release step, not a build step; it runs only inside `.github/workflows/release.yml`.
- `RELEASE.md` and `RELEASE_NOTES.md` describe upstream release flow, not this fork's flow.
